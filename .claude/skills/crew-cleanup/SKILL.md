# Crew cleanup — find the junk, ask before deleting

This is a project-authored skill, not a shipped one. It lives only under
`.claude/skills/crew-cleanup/` — do NOT copy it into
`cmd/harmonik/assets/skills/`. That directory is for skills every deployment
ships with; adding this one there makes it a fourth copy to keep in sync,
which is exactly what `skill-copy-governance` exists to prevent.

**One pass, not a subsystem.** This skill inventories, classifies, and (on
confirmation) deletes, once, when invoked. It does not run on a schedule, it
is not a daemon job, and it has no config surface. If a change to this skill
would add any of those, that change does not belong here.

## The sites it knows about

1. `.harmonik/crew/missions/*.md` — one file per crew mission. Cross-checked
   against the live crew registry (`.harmonik/crew/*.json`) and against
   references anywhere else in the repo.
2. `.harmonik/comms/cursors/` and `.harmonik/comms/cursors-live/` — comms
   cursor state. Unaudited: report only, do not propose a rule for these.
3. `.harmonik/cognition/` — relaunch scripts generated by Go code. Report
   only: this skill does not know the generator well enough to say a given
   file is safe to regenerate away.
4. `.harmonik/beads-owned/` — unaudited. Report only.
5. Repo root `HANDOFF-*.md` — cross-checked against references elsewhere in
   the repo.
6. `.harmonik/context/*.diff` and `.harmonik/context/*.patch` — raw patch
   files parked in the directory a captain boot-reads. Cross-checked against
   references elsewhere.

Never touch `.beads/` — the ledger has its own retention story.

## Step 1 — Run the scanner

```
bash .claude/skills/crew-cleanup/scan.sh
```

Run it from the repo root (it `cd`s to the repo root itself, so it is safe to
invoke from anywhere inside the tree). It is read-only — it inventories and
cross-references, and does not write or delete anything. It needs plain
`grep`, `find`, and `stat`; it does not depend on `rg` being on `PATH`
(`rg` is sometimes only a shell alias, not a real binary, in an interactive
session — the script does not assume it).

For each site the scanner prints a `SITE` block: item count, total size in
bytes, and the age in days of the oldest item. For the sites it knows how to
cross-check (missions, root HANDOFF files, context diffs/patches) it also
prints one `ITEM` line per file with:

- `LIVE=` — for missions only: whether the crew name appears in a
  `.harmonik/crew/*.json` registry file. `unknown (no registry files found)`
  means there is no registry to check against — do not read that as "not
  live".
- `REFS=` — how many other files in the repo mention this file's name.
- `REASON=` — the scanner's candidate reason. Treat this as a starting
  point, not a verdict — read on.

For the report-only sites (comms cursors, cognition, beads-owned) it prints
an `UNCLASSIFIED` line explaining why it isn't proposing a rule.

## Step 2 — Turn signal into a proposal, by hand

The scanner's `REASON` field is a heuristic, not ground truth. Before folding
an item into the deletion proposal:

- **A reason must name a fact, not a feeling.** "No live crew and no
  reference elsewhere" is a reason. "Old" is not — age alone never justifies
  a delete under this skill; it only tells the operator how long the state
  has been accumulating.
- **`REFS=0` is a starting point, not a verdict.** The scanner's reference
  check is a plain filename grep across the repo; it will not catch every
  form of reference (a reference by crew name alone rather than filename, a
  reference from a file the grep can't read, generated content). If an item
  looks otherwise load-bearing — its content describes ongoing work, or its
  crew name shows up in a bead or a plan doc even though the exact filename
  doesn't — do not add it to the deletion set on `REFS=0` alone.
  Skim the file first.
- **`LIVE=unknown (no registry files found)`** means the scanner had no
  registry to check, not that the crew is dead. Look for
  `.harmonik/crew/*.json` yourself (or ask whether the daemon is running —
  a live registry is daemon state) before treating a mission as unreferenced.
- **Report-only sites never enter the deletion proposal automatically.**
  Look at what's actually there. If a clear, nameable rule falls out (e.g. a
  cursor file naming a crew that is also dead by the same test used for
  missions), say so with that reason. Otherwise leave the whole site in the
  "could not classify" bucket — do not propose deleting an unaudited
  directory wholesale just because nothing referenced it in your search.

Build two lists:

- **Proposed for deletion** — path, reason, one line each.
- **Could not classify** — path, and why (ambiguous reference signal, no
  registry to check, unaudited site, anything else). This list is required
  even if it's short: reporting "found nothing I couldn't classify" is fine;
  silently dropping ambiguous items into either bucket is not.

## Step 3 — Report, then ask

Print both lists to the operator: site name, count, total size, oldest-item
age per site, then the proposed-deletion items with their reasons, then the
could-not-classify items with why. Then ask, plainly, whether to proceed —
do not delete anything until the operator answers yes.

If the operator wants to delete a subset, or asks a question, or says no:
answering no must leave the tree completely untouched. Only delete files the
operator explicitly confirmed, one `rm` per confirmed path (or `rm -r` for a
confirmed directory) — never a wildcard sweep of a whole site, since that
would also take unclassified items along with it.

## Notes for future edits to this skill

- Keep it to this one `SKILL.md` plus `scan.sh`. If a third file, a new
  config knob, or a scheduled trigger seems necessary, that is a sign this
  has grown into the cleanup subsystem the operator declined to build — stop
  and say so instead.
- `scan.sh` must keep working under a bare `bash` with a minimal `PATH` — it
  is invoked as a subprocess, not sourced into an interactive shell, so
  aliases and shell functions from `.zshrc`/`.bashrc` are not available to
  it.
