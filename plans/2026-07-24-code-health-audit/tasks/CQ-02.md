## Decisions that must be settled

1. **Canonical topology and compatibility.** Reconcile singleton
   `.harmonik/queue.json` wording with named queues under
   `.harmonik/queues/<name>.json`. Define which layouts are readable, writable,
   migrated, archived, and rejected. Preserve supported file formats unless an
   explicit operator decision is required.
2. **One mutation owner.** Name the production transaction owner and the exact
   lock/generation rule that serializes RPC, workloop, lifecycle, operator,
   eager-refill, budget, review-failure, startup, inline, and placeholder
   callers. State whether direct persistence remains legal anywhere.
   Generations are volatile, process-local stale-snapshot guards only; they
   are never persisted and never used as restart identity.
3. **Immutable transaction input.** Define clone → validate → mutate → persist
   → install ordering. A stored/live queue pointer must never expose an
   uncommitted mutation. Define generation/CAS behavior for stale snapshots
   and classify request/candidate validation plus stale-generation rejection
   as `rejected` before namespace I/O.
4. **Persistence result taxonomy.** For create, temp write, file sync, close,
   rename, parent-directory open, sync, and close, define results that
   distinguish:
   - definitely not committed;
   - committed and directory-durable;
   - indeterminate after namespace mutation.
   Specify retry, reload/reconcile, degraded-state, mutation refusal, and
   operator visibility for each result. A plain error that callers can
   misinterpret as “nothing changed” is not sufficient after rename/unlink.
   Marshal, candidate-temp write/sync/close, derived-event construction, and
   every filesystem failure before durable intent creation are
   `not_committed`; validation and stale generation are not included in that
   category. Once the intent is durable, later cuts are classified by the
   exact intent/canonical/temp state rather than collapsed into
   `not_committed`.
5. **Memory and event visibility.** For every result category define whether
   the QueueStore installs, retains, reloads, or clears state; when Wake is
   legal; and which domain events may be attempted. Preserve QM-063's durable
   before emit rule while making the authority boundary explicit: queue state
   and queue-owned transaction records decide commit, cleanup, restart, and
   admission; JSONL is observational per EV-021/EV-022 and never decides
   whether a queue mutation committed.

   Every ordinary canonical replacement—create, submit, append, reservation,
   Run-ID patch, activation/advance, pause/resume, eager refill, budget/review
   charge, maintenance/reconciliation, startup, inline/bootstrap,
   crew-placeholder creation, and cancelled-state replacement before
   archive—must use
   `.harmonik/queues/<normalized-name>.replace-intent` as exact
   restart-visible comparison evidence. The protocol order is mandatory:
   snapshot/validate/clone/mutate/marshal; write, fsync, and close the exact
   candidate temp; durably create the replace intent; only then mutate the
   canonical namespace. Validation and stale input are `rejected`. Marshal,
   candidate-temp, and derived-event construction failures before durable
   intent creation are `not_committed`.

   The replace intent records transaction ID, operation, queue/canonical
   identity, exact prior/candidate byte digests, selected already-durable temp
   basename, and Wake requirement. It is not an event outbox and records no
   event ID, effect key, replay cursor, response, or event-delivery state.
   For a final `complete-success` transaction only, the daemon preallocates
   `receipt_id` before installing the completed canonical candidate and the
   durable replace intent additionally records the exact receipt basename,
   receipt schema version, canonical receipt bytes, and SHA-256 digest of
   those exact bytes. The intent is durable before the completed canonical
   install and remains until both receipt durability and canonical unlink
   directory durability are classified. Recovery MUST reuse this bound ID,
   basename, schema, and byte string; it MUST NOT mint a second ID, rebuild
   receipt content from current time, or select a receipt by directory scan.
   Once the canonical transaction is classified and its
   namespace durability is resolved, event failure cannot roll back the
   mutation, retain a refusal solely for JSONL, or prevent intent removal.
   Wake is repeatable only after durable install. RPC responses are never
   persisted or replayed. The Class O `queue_cancelled_operator` audit remains
   separate from both replacement and completion records.
6. **Admission and group activation.** Settle whether submit plus first-group
   activation is one transaction or two ordered transactions, and the exact
   placement of `queue_submitted` and `queue_group_started`.
7. **Completion landmark.** Define the exact order among item/group terminal
   mutation, completed-state persistence, a queue-owned completion receipt,
   canonical unlink/directory sync, QueueStore clearing, and derived final
   `queue_group_completed` delivery. Cover both normal workloop completion and
   startup reconciliation. QM-051 owns the final state transition but neither
   cleans up nor emits the final event. QM-053 is the sole completion owner.

   The authoritative completion landmark is an immutable, directory-durable
   receipt at
   `.harmonik/queues/.completion-receipts/<queue_id>--<receipt_id>.json`,
   keyed by the composite `(queue_id, receipt_id)`. `receipt_id` is a
   daemon-minted UUIDv7 preallocated once and durably bound by the
   final-completion replace intent before completed canonical installation.
   The receipt basename is exactly
   `<queue_id>--<receipt_id>.json`; both components are canonical lowercase
   UUID strings, so `--` is unambiguous. Receipt schema version 1 has one
   canonical JSON encoding, and the exact canonical bytes recorded in the
   intent bind its transaction ID, normalized queue name, final group
   index/status/counts, completion timestamp, and SHA-256 digest over the
   exact completed canonical bytes. Recovery writes only those intent-bound
   receipt bytes to that intent-bound basename. The receipt is durable before
   canonical unlink.

   The flat `.completion-receipts` directory is capability-owned
   infrastructure. At startup/upgrade, before queue readiness or recovery,
   create it with `mkdir`; classify `EEXIST` as success only after opening and
   verifying it is the expected directory, classify a definite pre-mutation
   failure as not created, and classify any ambiguous create as requiring
   reload/reconciliation. After a successful first create, open/fsync/close
   `.harmonik/queues` before proceeding. Receipt creation uses a unique temp
   in the already-durable receipt directory, write/fsync/close, rename to the
   exact bound basename with no-replace/idempotent-exact-byte classification,
   then open/fsync/close `.completion-receipts`. No readiness or canonical
   unlink is allowed until the receipt directory and receipt entry are
   classified durable. The flat layout intentionally creates no per-queue
   directory.

   Cleanup is CAS-safe: it may unlink only a canonical file whose queue ID and
   exact completed digest match the receipt. A missing path is an idempotent
   cleanup success; a same-name canonical carrying another queue ID is a newer
   queue and MUST NOT be touched.

   The receipt survives canonical unlink and same-name reuse. Resubmission may
   reuse the name after old unlink plus parent-directory sync and ownership
   release, regardless of whether the old observation was appended. The
   old receipt and every late event remain scoped to the old queue ID. Define
   bounded retention and an explicit crash-safe GC protocol: retain every
   receipt until cleanup directory durability and ownership release are
   resolved, then for at least 30 days; afterward GC may unlink the receipt
   and open/fsync/close `.completion-receipts`, with absent treated as
   idempotent success and ambiguous unlink-or-parent-sync cuts resolved by
   directory reload before retry. There is no empty per-queue directory to
   remove. GC is forbidden while cleanup or its admission handoff is
   unresolved and never blocks admission.

   `queue_group_completed` is derived observation, never completion authority.
   For the final `complete-success` group only, QM-053 attempts it once on the
   normal path after receipt durability and before returning from the
   completion operation, and the optional `completion_receipt_id` field MUST
   be present with the exact intent-bound receipt ID. The field MUST be absent
   on every non-final `complete-success` observation and every
   `complete-with-failures` observation. The receipt stores no persistent
   event-delivery state, event ID, effect key, or replay instruction. Append
   failure is diagnostic; crash before or after the attempt may leave the
   event absent, and restart never synthesizes or retries it. Event outcome
   never gates unlink, QueueStore clear, readiness, receipt GC, or same-name
   resubmit.

## Required crash matrix

The design must give an unambiguous result and recovery action for:

- temp create, write, file sync, and close failures;
- canonical rename failure;
- target rename success followed by directory open/sync/close failure;
- completed-state persist before final event;
- canonical unlink failure;
- unlink success followed by directory failure;
- shutdown cancel persist and archive rename at every boundary;
- universal replace-intent create, write, file sync, close, namespace
