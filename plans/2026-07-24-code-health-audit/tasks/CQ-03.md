# CQ-03 — Own one durable dispatch reservation

## Dispatch metadata

- Group / priority: core queue / P0
- Execution profile: `sol_xhigh`
- Reviewer profile: `sol_xhigh`
- Depends on: `CQ-01`, `CQ-02I`
- Work type: shared-spine concurrency/recovery contract

## Objective

Create one serialized owner for queue item reservation: pending → dispatched
with an immutable Run ID, durably persisted before Bead claim/launch. Remove
nonfatal persistence holes and production-reachable unlocked/direct fallbacks.

## Evidence to verify first

Use `CQ-00` and `JR-00`. In current `runWorkLoop`, verify the two-step behavior:
the item is persisted as dispatched with no Run ID, persistence failure is
treated nonfatally, a Run ID is later patched and another persistence failure is
also nonfatal, then `ClaimBead` runs. Re-derive exact symbols before editing.

## Exclusive lease

- the dispatch-stamp/reservation region of `internal/daemon/workloop.go`
- exact queue wiring/locked-store APIs required by that region
- focused dispatch reservation, persistence-failure, race, and restart tests
- no claim-to-run record semantics (`JR-01`), terminalization (`JR-03`), or Pi
  behavior

This is the sole `dispatch-spine` writer while active.

## Required work

1. Define the persisted reservation record and ordering using existing fields
   unless a reviewed contract proves a schema addition necessary.
2. Add failing tests for persistence failure before reservation, failure after
   Run ID mint, concurrent ticks, cancellation, and restart.
3. Make exactly one claimant win and make durable-write failure fail closed
   before `ClaimBead`.
4. Ensure retry/reclaim can distinguish unclaimed reservation, claimed run, and
   terminal item without guessing from events.
5. Remove or make unreachable every alternate production mutation path.

## Acceptance

- No persisted `dispatched` item lacks the Run ID needed to correlate recovery.
- No Bead claim or launch follows a failed reservation persist.
- Concurrent dispatch ticks cannot reserve the same item twice.
- Restart can deterministically retry, adopt, or fail the reservation.
- Every queue mutation in this path occurs under the single mutation owner.

## Verification

Focused failing-first tests, `go test -race`, persistence fault injection,
controlled restart scenario, scoped vet/lint, UBS, Sol cross-group review, and
`make check-fast`.

## Escalate when

Stop before implementation if correctness requires a new queue schema/CAS
generation or a spec decision about claim-versus-reservation authority. Produce
the decision packet; do not improvise the invariant.

## Return

Use the directory return contract. **COMMIT EXPLICITLY.**
